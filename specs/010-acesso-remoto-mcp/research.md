## Decisões

### R-1 — Hospedagem: Cloud Run, escala a zero, no projeto `actual-financas`

- **Decisão**: um serviço **Cloud Run** em `us-east1` (mesma região da VM), `min-instances=0`, **`max-instances=1`**, 512 MiB, 1 vCPU, com _startup CPU boost_. Entrada pública (a autenticação é nossa).
- **Justificativa**: o Pedro decidiu **24h** e **até R$ 20/mês**. Cloud Run é o único candidato que atende os dois sem tocar a VM: no uso do casal (dezenas de pedidos por dia) cabe na cota gratuita; o custo residual estimado é de centavos (imagem no Artifact Registry, versões de secrets) — **estimativa a confirmar na fatura**, com o alerta de orçamento já existente em `budget.tf`. `max-instances=1` limita custo e memória por construção, e permite manter estado de curta duração em memória sem coordenação.
- **Alternativas**:

| Alternativa                                   | Por que não                                                                                                                                                                                                                                                                                                                                                                |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **(b) Mac do Pedro com túnel HTTPS**          | Descartada pela decisão de **24h**: some quando o Mac dorme ou sai da rede. Também prenderia o acesso a um túnel de terceiro                                                                                                                                                                                                                                               |
| **Na própria VM `e2-micro`** (novo container) | Evita fornecedor novo e deixa o estado em SQLite local, mas: (1) o princípio V manda trabalho que não é o Actual rodar **fora** da VM; (2) o teto de 384 MB já é do Actual e a RAM restante (≈1 GB no total) é compartilhada com SO e Caddy; (3) um serviço público com parser OAuth ficaria no mesmo host dos dados e dos backups; (4) RF-025 exige não degradar o Actual |
| **Cloud Run com `min-instances=1`**           | Elimina partida a frio, mas custa de ordem de US$ 10/mês só de instância ociosa (estimativa) — metade do teto por um ganho de segundos                                                                                                                                                                                                                                     |
| **Outro PaaS / Workers / Fly.io**             | Cria um **terceiro novo fora do GCP** para declarar e vigiar. Workers nem roda o cliente do Actual (módulo nativo de SQLite)                                                                                                                                                                                                                                               |
| **Cloud Functions / App Engine**              | Mesma família do Cloud Run, com menos controle de concorrência, de instâncias e de volume de secrets                                                                                                                                                                                                                                                                       |

- **Consequência**: partida a frio existe (alguns segundos). Mitigação em R-12.

### R-2 — Protocolo: MCP por HTTP "stateless" em `POST /mcp`

- **Decisão**: transporte HTTP do SDK oficial em modo **sem sessão** (um servidor MCP novo por requisição), resposta JSON simples (sem SSE), `GET`/`DELETE` em `/mcp` devolvem `405`.
- **Justificativa**: com escala a zero, sessão em memória some a qualquer momento. Sem sessão não há o que perder, e cada requisição carrega seu próprio `Authorization` (a spec já exige isso).
- **Alternativa**: sessões com `Mcp-Session-Id` — frágil com instância que desaparece e sem ganho para ferramentas de consulta.

### R-3 — Autorização: servidor OAuth **embutido** no mesmo serviço, sobre o roteador do SDK

- **Decisão**: o serviço é, ao mesmo tempo, _recurso_ (`/mcp`) e _servidor de autorização_ (`/authorize`, `/token`, `/register`, `/revoke`, metadata). Usa o roteador e o middleware de bearer do SDK oficial do MCP, com um provedor nosso por trás. `authorization_servers` aponta para o próprio serviço.
- **Justificativa**: reaproveitar o código que o SDK mantém (PKCE, validação de redirect, erros RFC 6749, parser de formulário, metadata) reduz a quantidade de código de segurança _nosso_. Um único serviço evita uma segunda hospedagem. Contratos em `contracts/oauth-flow.md`.
- **Alternativas**: IdP gerenciado (Auth0, Cognito, Firebase Auth) — terceiro novo + custo + limites de DCR; servidor de autorização separado — dobra a superfície; **segredo estático/API key** — rejeitado pela spec e pelo comportamento do Claude (beta só para organizações).
- **Spike S-1**: confirmar na versão fixada pela 005 (`@modelcontextprotocol/sdk` 1.32.1) que o roteador aceita um _client store_ customizado, trata `resource` e devolve `401` com `WWW-Authenticate`. Plano B: implementar só os endpoints faltantes, mantendo os mesmos testes de contrato.

### R-4 — Registro de cliente (DCR) **sem estado**, com política de redirects por lista configurável

- **Decisão**: `/register` não grava nada. O `client_id` devolvido é um **documento assinado** (HMAC) que carrega os `redirect_uris` e o nome do cliente. O registro só é aceito se **cada** redirect casar com a **política de redirects**: (a) `https` com host e caminho numa **lista configurável** (padrão: `claude.ai/api/mcp/auth_callback`, `claude.com/api/mcp/auth_callback`, `chatgpt.com/connector/oauth/*`, `chatgpt.com/connector_platform_oauth_redirect`); (b) _loopback_ (`localhost`, `127.0.0.1`, `[::1]`) com **porta livre**, como manda o RFC 8252 — é o que CLIs e IDEs usam. Qualquer outro host é recusado. Cliente público (sem segredo). Acrescentar um provedor novo = **uma linha de configuração**, sem código (RF-028).
- **Justificativa**: `/register` é anônimo; gravando, qualquer um encheria o estado. Assinado e sem estado, spam não custa nada. A lista fechada de redirects é o que impede um atacante de registrar um cliente com retorno para o domínio dele e induzir alguém a consentir (_confused deputy_); a tela de consentimento mostra o nome e o host do retorno como segunda barreira.
- **Sem CIMD na v1**: aceitar `client_id` em forma de URL obrigaria o servidor a **buscar** um documento externo (risco de SSRF e de latência dentro dos 10 s do Claude). Como não anunciamos o suporte, o Claude cai em DCR e o ChatGPT também aceita DCR (F-13). CIMD fica como evolução, restrita a hosts conhecidos.
- **Alternativa**: lista de redirects apenas do Claude — mais simples, mas falha o requisito de qualquer provedor (RF-028).

### R-5 — Identidade: **login Google** (OIDC) + lista de autorizadas

- **Decisão**: no `/authorize` o navegador vai ao Google (fluxo _authorization code_, segredo do cliente só no servidor, `nonce` e `state` assinados), com escopo `openid email`. Volta em `/google/callback`; o servidor valida `iss`, `aud`, `exp`, `nonce`, `email_verified` e confere o e-mail com a **lista de autorizadas**. **Descarta** os tokens do Google na hora e **nunca grava o e-mail**.
- **Justificativa**: é "entrar com a conta que o casal já usa" (RF-005) — nada para decorar, copiar ou digitar. O cliente OAuth do Google é **novo e separado** do que o Actual usa, para isolar segredo e redirect.
- **Lista de autorizadas** (RF-006, RF-017): arquivo JSON `{ "pedro": "…", "julia": "…" }` num **secret montado como arquivo**, relido a cada ≤ 30 s. Mais de 2 entradas ou arquivo ilegível ⇒ **recusa tudo** (falha fechada). Editar o secret pelo console do GCP (de qualquer navegador, inclusive do celular) entra em vigor em ≤ 1 min, sem deploy.
- **Alternativas**: senha própria (viola "nada para digitar"); passkeys/TOTP próprios (mais código de segurança nosso); aceitar qualquer conta Google (exigiria depender só do modo "usuários de teste" do Google — camada única).
- **Spike S-5**: confirmar que o cliente OAuth novo, em modo de teste com Pedro e Julia como usuários de teste, emite `id_token` com `email`.

### R-6 — Tokens: acesso curto (JWT) + refresh rotativo, **checados contra o estado a cada pedido**

- **Decisão**: _access token_ = JWT assinado (HS256, `node:crypto`), `aud` = URL do `/mcp`, validade **15 min**. _Refresh token_ = opaco, **rotativo**, guardado só como hash; reuso de um refresh já trocado **encerra o acesso inteiro**. Inatividade de **30 dias** expira o acesso (janela deslizante); teto absoluto de **180 dias** força nova autorização. Toda requisição confere se o acesso (`gid` do JWT) continua **ativo** no estado (cache ≤ 30 s).
- **Justificativa**: a checagem a cada pedido faz a revogação valer em **≤ ~1 min** (RF-015 pede ≤ 5). Tokens curtos limitam o estrago de um vazamento (spec MCP, _Token Theft_). A rotação é exigida pelo Claude (F-4).
- **Segredo mestre** (`MCP_SEGREDO_ASSINATURA`, ≥ 32 bytes, Secret Manager): subchaves por finalidade via HKDF (tokens, `client_id`, `state`, CSRF, código de autorização). Trocá-lo **invalida tudo** (segunda chave-mestra de emergência).
- **Alternativa**: tokens opacos gravados a cada emissão — mais escritas no estado sem ganho; JWT de longa duração — revogação lenta.

### R-7 — Estado: **um objeto JSON no GCS**, sem SDK

- **Decisão**: `estado.json` num bucket privado dedicado (acesso uniforme, prevenção de acesso público, versionamento com ciclo de vida curto para recuperação). Escrita com **`ifGenerationMatch`** (concorrência otimista, com _retry_). Acesso por REST com o token da conta de serviço (servidor de metadados) — **sem** `@google-cloud/storage`. O CLI do Pedro usa a mesma camada, com `gcloud auth print-access-token`.
- **Conteúdo**: apenas os **acessos** (rótulo, pessoa, datas, hashes) e um carimbo `revogadoAntesDe`. Códigos de autorização e estado de login vivem em memória/assinados (60 s – 10 min). Escritas: ao conceder, rotacionar refresh, encerrar e, no máximo a cada 10 min, ao registrar "último uso". Dezenas por dia: dentro da cota gratuita.
- **Justificativa**: o Cloud Run não tem disco persistente; o mínimo que dá para **listar e encerrar** acessos (história 2) é um pequeno documento durável.
- **Atenção à constituição (V)**: "NÃO DEVE introduzir banco externo". Um objeto JSON de poucos KB com a lista de acessos **não é o banco do produto** (que segue SQLite no Actual), mas é estado externo. Registrado no _Rastreamento de Complexidade_ do plano.
- **Alternativas**: Firestore (é um banco externo de verdade — viola V); SQLite na VM (acopla ao Actual e à VM, R-1); tudo sem estado (não permite listar nem encerrar um acesso individual).

### R-8 — Credencial do Actual: token de sessão **só no Secret Manager**

- **Decisão**: o serviço lê o Actual com o **token de sessão do Pedro** (o mesmo que a 005 usa localmente), montado a partir do Secret Manager (`ACTUAL_SESSION_TOKEN`, `ACTUAL_SERVER_URL`, `ACTUAL_BUDGET_SYNC_ID`, e a senha do orçamento se houver). Conta de serviço do Cloud Run com `secretAccessor` **apenas** nesses secrets e acesso ao bucket de estado **apenas**. Nada disso chega ao Claude, ao celular ou à tela de conexão (RF-009).
- **Risco residual (registrado)**: o token é equivalente a uma senha e, no Actual, **também escreve**. Se o ambiente do serviço fosse comprometido, o atacante poderia escrever no Actual mesmo que _nosso código_ seja só leitura. Mitigações: sem shell/exec no Cloud Run, SA mínima, imagem sem ferramentas, rotação documentada. Alternativa mais forte (conta Google _dedicada_ para o serviço) não reduz o poder de escrita no Actual hoje (não há papel só-leitura), então **fica como melhoria futura**, não requisito.

### R-9 — **Paridade com o Mac**: o protocolo passa a morar no servidor

- **Decisão**: o texto de _Definições_ e _Protocolo de resposta_ do subagente (despesa/receita externas, `sobra = receita − despesa (provisório)`, período explícito, nunca devolver zeros sem dados, recusar escrita, bloco de confiança/completude) vira um módulo `protocol.ts` e é entregue ao cliente no campo **`instructions`** do MCP e nas descrições das ferramentas. O subagente local continua existindo; **um teste** compara as frases-chave dos dois para não divergirem.
- **Justificativa**: F-8 — sem isso, o celular responderia com os mesmos _números_, mas sem as mesmas _regras_ (RF-002, CS-003 ficariam só parcialmente verdadeiros).
- **Limite honesto**: `instructions` é orientação ao modelo, não garantia. O que **não pode falhar** continua garantido por código: somente leitura (não há ferramenta de escrita), máscara de PII (toda resposta passa por `maskDeep`), exclusão de transferências (dentro das ferramentas).
- **Dependência**: o bloco de completude e as ferramentas de duplicatas e compromissos pertencem à evolução da 005 (histórias 2 e 3). Esta feature entrega **paridade com o que a 005 tiver**: toda ferramenta nova nasce em `createFinancasServer` e aparece nos dois caminhos.

### R-10 — Frescor dos dados

- **Decisão**: a fonte recebe `refresh()`; antes de uma consulta, se a última sincronização do orçamento tiver mais de **5 min**, sincroniza. Toda resposta ganha `atualizado_em`.
- **Justificativa**: instância quente mantém o orçamento em memória por até ~15 min; sem refresh o celular ficaria _menos_ atualizado que o Mac (spec, caso de borda).

### R-11 — Camadas de proteção além do OAuth

| Camada                                                                                                                        | Efeito                                                                                                                                                                                             |
| ----------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Origem (opcional, DESLIGADA por padrão)**: lista de faixas de IP por provedor para `/mcp`, `/token`, `/register`, `/revoke` | Cada provedor publica faixas próprias e as muda; ligar por padrão quebraria a promessa de "qualquer provedor" (RF-028). Fica como endurecimento para quem usa só o Claude (`160.79.104.0/21`, F-5) |
| **Limites em memória** (por IP, por acesso)                                                                                   | Falhas de autenticação, `/register` e consultas por acesso são freados com `429`; protege o Actual (RF-019, RF-025)                                                                                |
| **Cabeçalhos e corpo**: sem CORS, corpo ≤ 100 kB, `Origin` presente e estranho ⇒ `403`                                        | Fecha DNS rebinding e uso por página web de terceiros                                                                                                                                              |
| **Páginas de login/consentimento**: CSP restritiva, `frame-ancestors 'none'`, CSRF, `no-store`, exibem o domínio do redirect  | Evita clickjacking e consentimento forjado (spec MCP, _Confused Deputy_)                                                                                                                           |
| **Teto de acessos** (10 ativos por pessoa)                                                                                    | Um login legítimo repetido não incha o estado                                                                                                                                                      |

- **IP não é registrado**: só é usado em memória pelos limites (F-11).

### R-12 — Partida a frio e latência

- **Decisão**: os endpoints de descoberta, `/register`, `/authorize` e `/token` **não dependem do orçamento do Actual**; respondem em milissegundos mesmo na primeira chamada da instância (limite do Claude: 10 s, F-3). O orçamento é aberto **em segundo plano** no início da instância; a primeira ferramenta espera a abertura (com teto de tempo e erro distinguível, RF-022).
- **Meta**: primeira pergunta após longa inatividade em < 30 s (CS-002); medir no quickstart. Se falhar, escalonar com _startup CPU boost_ (já ligado) e, por último, `min-instances=1` com nova decisão de custo.

### R-13 — Logs: auditoria própria, sem PII, e **sem log de requisições da plataforma**

- **Decisão**: o serviço emite **uma linha JSON por evento** em stdout: `{ ts, evento, rotulo, ferramenta?, resultado, motivo? }`. Eventos: `acesso_concedido`, `acesso_renovado`, `acesso_encerrado`, `consulta`, `recusado`. **Nunca**: e-mail, IP, descrição, valor, parâmetros da consulta, tokens, `code`. Contrato em `contracts/auditoria.md`.
- Os **logs de requisição do Cloud Run** (URL com `code=`/`state=`, IP) são **excluídos** por filtro no Cloud Logging (Terraform), como o Caddy já faz.
- **Histórico para o Pedro** (História 2, cenário 6): `gcloud logging read` pelo CLI de administração.

### R-14 — Administração: CLI + console do GCP, **sem endpoint administrativo na internet**

- **Decisão**: `acessos` (CLI na máquina do Pedro, autenticado por `gcloud`) com `listar`, `encerrar <id|rótulo>`, `encerrar-todos`, `historico`. Emergência **sem Mac**: editar o secret de autorizadas (esvaziar) no console do GCP, que vale em ≤ 1 min. Contrato em `contracts/cli-acessos.md`.
- **Justificativa**: um painel web administrativo seria mais uma superfície pública protegendo exatamente o que queremos proteger. IAM do GCP já governa quem administra.
- **Alternativa futura**: página `/acessos` atrás do mesmo login Google, para a Julia encerrar o próprio acesso sem o Pedro. Fora desta versão.

### R-15 — Domínio: URL estável `*.run.app`

- **Decisão**: v1 usa o endereço do próprio Cloud Run; o `PUBLIC_URL` é fixado por configuração e entra no `resource` e no `iss`.
- **Consequência**: trocar para domínio próprio depois muda o `resource` e exige **reautorizar** os aparelhos (um login rápido cada). Aceitável; evita DNS e certificado agora.

### R-16 — Build e deploy: adaptar a esteira do `smartdata-platform`, sem copiá-la inteira

- **O que se aproveita** (F-12): build de imagem + `gcloud run deploy` com `--set-env-vars`/`--set-secrets`, autenticação por **WIF** (sem chave JSON, como o `deploy-gce.yml` daqui já faz), `concurrency` por serviço **sem cancelar deploy em andamento**, _labels_, `startup_cpu_boost`, `min_instances: 0`, secrets e permissões de secret **gerenciados no Terraform** (o CD não recebe poder de administrar IAM), **smoke test pós-deploy** e _rollback_ para a revisão anterior se ele falhar.
- **O que não se traz**: o despachante por `execution_plan.yaml` e os workflows reutilizáveis (Python, Next.js, Cloud SQL, migrações, Scheduler, Cloudflare DNS) — resolvem uma frota de apps; aqui é **um** serviço. Menos peças, menos o que vigiar.
- **Decisão**: imagem própria (`packages/custom/Dockerfile.mcp-remoto`; Node ≥ 22.18 para rodar TypeScript direto como a 005; dependências só do pacote `custom`) no **Artifact Registry** com política de limpeza (manter as últimas 3); workflow **novo** `deploy-mcp.yml` (disparo por `packages/custom/**` e `infra/mcp-remoto.tf`), com service account **própria** (`mcp-deployer`) no WIF existente; smoke test: `POST /mcp` sem token ⇒ `401` com `WWW-Authenticate`, e `/.well-known/oauth-protected-resource` ⇒ `200`. `deploy-gce.yml` ganha exclusão de `packages/custom/**` para **não redeployar o Actual** quando só o MCP muda (F-10). Recursos no **novo** `infra/mcp-remoto.tf`.
- **Alternativas**: reaproveitar a `app-deployer` (acumularia poderes de Cloud Run no papel que mexe na VM); GHCR (Cloud Run não puxa de GHCR direto); `gcloud run deploy --source` (builda no Cloud Build — outro serviço pago por minuto, sem cache controlável).
- **Domínio próprio**: o smartdata usa _domain mapping_ + CNAME. Aqui a v1 fica em `*.run.app` (R-15); a esteira deixa um passo opcional de domain mapping para quando o Pedro quiser, ciente de que trocar o endereço pede nova autorização dos aparelhos.
- **Spike S-6**: confirmar que `yarn workspaces focus @actual-financas/custom --production` monta uma imagem enxuta e que o módulo nativo do SQLite do cliente do Actual instala em `node:*-slim`. Plano B: `npm install` isolado em `packages/custom`.

### R-17 — Interoperabilidade: um servidor, vários provedores

| Provedor / cliente                    | Como conecta                                                                 | O que o servidor precisa                                       | Como se garante                                         |
